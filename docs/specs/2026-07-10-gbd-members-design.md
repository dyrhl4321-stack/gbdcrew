# 근방단 회원 명부 `gbd_members.html` (설계)

2026-07-10 · 대상: `Desktop/근방단/출첵어플`

## 문제

출석체크 앱은 회원 정보를 어디에도 담고 있지 않다. 통계는 모임 문서(`gbd_meetings`,
`gbd_archive`)의 `members` 배열에 적힌 **이름만** 모아서 집계한다.

그런데 근방단 규칙에는 출석 횟수와 무관한 조항이 따로 있다.

- **신규(병아리)**: 가입 후 1개월이 지나도록 한 번도 안 나오면 퇴출
- **기존**: 이번 달과 지난 달, 두 달 연속 출석 0회면 퇴출

이 판정에는 **가입일**이 필요한데 앱에 그 필드가 없다. 그래서 운영진이 엑셀로 따로
관리해 왔고(`유령회원 정리 0709.xlsx`), 앱의 출석 데이터와 손으로 대조하고 있다.

## 목표

운영진이 한 화면에서 회원 명부를 관리하고, **퇴출 판정을 자동으로 본다.**
`index.html` 은 건드리지 않는다.

## 데이터

### 새 컬렉션 `gbd_members`

문서 하나가 회원 한 명. 문서 id 는 이름(실명).

```json
{
  "name": "김서경",
  "nickname": "",
  "birth": 2000,
  "region": "중랑",
  "type": "new",              // "new"=병아리, "old"=기존
  "joinDate": "2025-11-13",   // 병아리만. 기존은 null
  "status": "active",         // "active" | "removed"
  "memo": "",
  "createdAt": "...", "updatedAt": "..."
}
```

**이름이 곧 키다.** 모임 명단도 실명으로 적으므로 그대로 매칭된다.
닉네임은 소모임 앱에서 이상한 이름을 쓰는 사람을 알아보기 위한 **참고용 칸**이며,
매칭에는 쓰지 않는다.

`status: "removed"` 는 이미 나간 사람이다. **삭제하지 않고 숨긴다.** 되살릴 수 있고,
과거 출석 기록과의 연결도 끊기지 않는다.

### 출석 이력

`gbd_meetings` + `gbd_archive` 를 읽어 회원별로 셋을 계산한다.

| 값 | 정의 |
|---|---|
| `attendCount` | `status[i].attend` 또는 `.late` 인 지난(오늘 포함) 모임 수 |
| `lastAttendDate` | 그중 가장 최근 모임 날짜 |
| `recent2mo` | **이번 달 + 지난 달**에 열린 모임 중 출석/지각한 수 |

지각은 출석으로 센다. 취소·불참·미체크는 출석이 아니다.

## 판정 규칙

위에서부터 먼저 걸리는 것이 답이다.

| 순서 | 조건 | 표시 |
|---|---|---|
| 1 | `status == "removed"` | `제외됨` (회색, 판정 안 함) |
| 2 | 동명이인 (같은 이름 2명 이상) | `판정 보류 — 수동 확인` |
| 3 | 병아리 · 가입 후 1개월 미경과 | `유예 중 (D-12)` |
| 4 | 병아리 · 1개월 경과 · `attendCount == 0` | **`퇴출 대상`** |
| 5 | 기존 · `recent2mo == 0` | **`퇴출 대상`** |
| 6 | 그 외 | `정상` |

**병아리는 한 번이라도 출석하면 기존으로 졸업한다.** 첫 출석 시 `type` 을 `"old"` 로
바꾸고 `joinDate` 는 기록으로 남긴다. 이 규칙이 없으면 1년 전에 가입해 꾸준히 나오는
사람이 계속 병아리로 남는다 (실제로 2025-07-19 가입자가 있다).

"이번 달 + 지난 달" 은 **캘린더 월**이다. 7월엔 6·7월, 8월엔 7·8월.
대표 확인: "6~7월 합쳐서 한번도 안 나온 사람, 8월부터는 최근 2개월간 출석 0회".

## 화면

한 화면, 표 하나.

**상단** — 요약 숫자(전체 / 병아리 / 퇴출 대상 / 제외됨), 필터 버튼
(전체·병아리·기존·퇴출 대상·제외됨), 이름 검색.

**표** — 이름 · 닉네임 · 출생년도 · 지역 · 구분 · 가입일 · 출석 · 마지막 출석 ·
최근 2개월 · 판정 · 작업.

**병아리는 노란 형광 배지(🐤 병아리)**. 기존은 회색 배지. 퇴출 대상 행은 배경을
옅은 빨강으로 깐다. 제외됨은 흐리게.

**작업** — 수정(인라인), `제외` / `복원`, 새 회원 추가.

**명부에 없는 이름 경고** — 모임 명단에는 있는데 `gbd_members` 에 없는 이름을 표
아래에 따로 모은다. 두 데이터가 어긋나는 걸 바로 본다. 클릭하면 그 이름으로 회원을
추가할 수 있다.

## 접근 제어

`index.html` 과 같은 방식. 관리자 비번(5252) 입력 전에는 아무것도 안 보인다.
이 앱의 다른 화면과 동일하게 클라이언트 측 확인이며, Firestore 규칙이 진짜 방어선이다.

## 초기 데이터

`유령회원 정리 0709.xlsx` 를 정제해 121명을 넣는다.

정제 규칙 (실측 근거):

1. **미래 날짜는 작년으로 보정.** 오늘(2026-07-10)보다 뒤면 연도에서 1을 뺀다.
   `2026-11-13 → 2025-11-13`. 대표 확인 완료.
2. **시트1(121행) + 시트2(38명) 병합.** 이름이 키. 겹치는 사람의 가입일은
   두 시트가 완전히 일치하므로 충돌 없음.
3. **`김준성` 동명이인 정리.** 1994·송파구(병아리)는 이미 나갔으므로 버리고,
   1995·강남구(기존, 참석 O)만 남긴다. 대표 확인 완료.
4. 가입일이 있으면 `type: "new"`, 없으면 `"old"`.

결과: **121명 (병아리 47, 기존 74)**. 출생년도·지역은 전원 채워져 있다.

엑셀의 `모임 참석 여부(O/X)` 는 **넣지 않는다.** 출석은 Firestore 가 진실이다.
시딩 직후 그 값과 Firestore 계산 결과를 대조해 어긋나는 사람만 콘솔에 찍어
검증에만 쓴다.

시딩은 `gbd_members.html` 안의 "초기 데이터 넣기" 버튼으로 한 번만 실행한다.
이미 문서가 있으면 건너뛴다(덮어쓰지 않는다).

## 검증

엑셀 기준으로 **병아리 47명 중 37명이 퇴출 대상**, 기존 74명 중 참석 O 가 62명이다.
시딩 후 화면의 숫자가 이와 크게 어긋나면 매칭이 깨진 것이다 — 이름 불일치를 의심한다.

회귀로 확인할 것:

- 제외한 회원이 요약·판정에서 빠지는가
- 병아리가 첫 출석하면 기존으로 바뀌는가
- 동명이인이 생기면 자동 판정이 멈추는가
- 명부에 없는 모임 참석자가 경고 목록에 뜨는가

## 손대지 않는 것

- `index.html` — 출석/통계 화면
- `gbd_meetings`, `gbd_archive` 문서 구조
- 기존 경고 규칙(지각 2회 = 경고 1, 불참 1회 = 경고 1)

## 후속 (이번 범위 밖)

- 명부에 없는 이름을 모임 명단에서 자동으로 지우는 기능
- 퇴출 확정 시 모임 명단에서 일괄 제외
- 가입일 히스토리(재가입 추적)
